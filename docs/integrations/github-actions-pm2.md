# GitHub Actions and local PM2

Managed deployment is implemented for PM2 on the same machine as core-api. The verification agent is optional and does not execute deployments remotely.

1. Set CARF_LOCAL_INSTALLATION_ID on core-api to the GitHub App installation permitted to use this host. Leave it unset for a policy-only hosted service.
2. Link the repository and configure its exact PM2 target, Git working directory, build command, and health URL.
3. Grant the GitHub App Contents, Workflows, and Secrets write access plus Actions read access. Configure a successful push workflow named CI on the default branch.
4. Use the dashboard GitHub Actions integration to install the generated workflow and installation-scoped CARF_API_KEY secret.
5. Push a classified change. CARF verifies the CI run identity, repository, branch, and exact SHA before deploying. A dedicated Actions rollback job executes a persisted rollback request through core-api.

Example `.carf.yml`:

```yaml
mode: standalone
deploymentIntegration: github_actions
runtimeAdapter: pm2
adapter:
  kind: pm2
  target: api-server
  layout: git
  cwd: /srv/api
  buildCommand: npm ci && npm run build
  healthUrl: http://127.0.0.1:8080/health
  startupGraceSeconds: 60
```

The build command runs for deployment and rollback. Use `true` explicitly for applications with no build step. It must rebuild the checked-out revision rather than pull the branch tip.

The required workflow defaults to CI. A custom ciWorkflowName in repository connection storedConfig must match the workflow generated by the dashboard and the server verifier; a caller-supplied workflow name is ignored. Direct-push deployment cannot use the CARF deployment workflow itself as proof of CI.

Run the opt-in real PM2 suite and the hosted acceptance procedure in [validation](../validation/pm2-github-actions.md). Local success does not prove GitHub webhook delivery or reverse-proxy routing.
